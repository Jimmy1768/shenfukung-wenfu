## Frozen Governance Criteria

The completed source migration must establish all of the following:

1. Strategy is the single workspace cross-repository, durable-task-creation,
   and Thread Refresh owner. It creates or refreshes Control A only when no
   authoritative Control exists and Planning sends one valid task-lifecycle
   request.
2. Planning remains one unnumbered repository task. It freezes accepted plans
   and acceptance criteria, then sends ordinary repository work directly to
   the authoritative Control. Planning sends Strategy a lifecycle request only
   when no authoritative Control exists, a Control needs Thread Refresh, or a
   genuinely independent Control B must be created. It does not select a
   branch, execution mode, model/reasoning, exact owned paths, checks, or an
   implementation packet.
3. Control A is the default repository Control. Control B is created only for
   genuinely independent parallel work; it is not a standing partner or
   replacement slot and does not require Control A to be active.
4. Control alone selects its implementation branch, execution mode,
   implementation model/reasoning, exact owned paths, and required checks,
   then freezes one implementation packet.
5. Control normally dispatches and supervises one ephemeral Implementer,
   reviews frozen-plan conformance, locally integrates accepted work, and then
   sends exactly one terminal packet to Planning.
6. A persistent Handoff is an exceptional one-packet continuity mechanism,
   never a permanent Control pairing. Its use requires a recorded qualifying
   continuity reason.
7. Legacy numbered Controls and permanent-pair task IDs are non-authoritative,
   receive no new work, and remain preserved where their worktree state is
   unsafe or dirty. This migration does not delete, clean, reset, archive, or
   otherwise reconcile those lanes.
8. A terminally accepted Control A remains visible and idle after its terminal
   acceptance. It is not automatically archived. Any later Strategy archive
   requires an explicit Director archival instruction, the complete idle gate,
   and an exact current snapshot record.
9. Codex Work Mode remains builder governance only. It does not define temple,
   account, payment, deployment, Worker, Incarnation, Route, Step, Receipt,
   Handoff, reincarnation, or other product/runtime lifecycle semantics.
10. Existing repository safety remains intact: no unauthorized push,
    deployment, publication, external mutation, provider/secret access,
    production-data action, approval handling, or product/runtime change.
11. Cross-repository contract, architecture, sequencing, and authority work
    routes Planning to Strategy and then to the affected Planning tasks.
    Controls neither coordinate cross-repository architecture Control-to-
    Control nor freely interrupt another Planning task.
